## 1. システムの目的

セルフメディケーション推進アプリ「健康応援口座システム」（LINEミニアプリ）。
健保加入者に対し、健康行動（eラーニング・アンケート）→ 医療費比較 → OTC薬への切替・購入を促し、
データヘルス計画の成果指標（適正受診・服薬／医療費適正化）の改善に寄与する。

- **利用者（会員）**：健保の加入者。スマホのLINEアプリ内（LIFF）から利用（PC不可）。
- **運営管理者（ICP）**：別URLの管理画面（PC可・多要素認証）からコンテンツ・商品・集計を管理。
- LINE公式アカウントは健保ごとに開設する**マルチテナント**（保険者ID＝テナント）。

## 2. 全体構成

```
利用者(LIFF/スマホ) ─┐
                     ├─ ロードバランサー＋アクセラレーター(WAF)＋API Gateway(IP制限)
運営(管理画面/PC) ───┘        │
                              ▼
                     Laravel（APIサーバー、PHP）
                       ├─ PostgreSQL（Master/Slave）… 会員・ポイント・商品・ログ（非PII）
                       ├─ オブジェクトストレージ … 静的（画像・CSS）
                       └─ 外部連携（gateway層に隔離）
                            ├─ LINE（ログイン/IDトークン検証・Messaging API）
                            ├─ ペイジェント（決済・トークン化・3DS）
                            ├─ giftee for business（ポイント交換）
                            └─ 白石薬品（OTC発注CSV送付）

個人情報領域（サンプリ）… 加入者マスタ・受診情報（アプリ非保持。登録時に突合のみ）
```

- 実行環境は**さくらのクラウド（ISMAP）**。フロント／バック・個人／非個人を領域分離。医療情報システムガイドライン第7版準拠。
- **要配慮個人情報（受診情報）・カード情報はアプリに保持しない**。本人特定は登録時の加入者マスタ突合。

確定している前提:

- バックエンドは PHP 8.3以上（`composer.json` の制約。CI・開発環境は 8.4 / 8.5 を使用）/ Laravel 13、フロントは React + Vite + TypeScript + LIFF
- DB は PostgreSQL（ORM: Eloquent。更新Master・参照Slave）※現状の `config/database.php` は単一接続のみで read/write 接続の分離は未実装。Master/Slave構成の反映は別途実装タスクとして対応が必要
- 健康情報（要配慮個人情報）を扱う

## 4. レイヤ構成（backend）

機能ごとの縦割り（**モジュラモノリス**）。

```
backend/app/
├── Support/                  # 全機能で共有するもの（共通設定・共通例外・認証）
└── Features/
    └── <機能名>/
        ├── Http/Controllers/  # 入出力（HTTP）。ビジネスロジックを持たない
        ├── Http/Requests/     # 入力検証（Form Request）
        ├── Http/Resources/    # 出力整形（API Resource）
        ├── Services/          # ビジネスロジック。ここが本体
        ├── Models/            # 永続化・データ構造（Eloquent）
        ├── Gateways/          # 外部API呼び出しはここに閉じる（専用クライアント）
        └── Exceptions/        # この機能固有の業務例外
```

**依存の向き（守るべき制約）:**

- `Controller → Service → (Model / Gateway)` の一方向のみ。逆流させない。
- **機能間の直接参照は禁止。** 共有が必要なものは `Support/` に置く。
- `Model`・`Gateway` より下（DB・外部API）の型を `Controller` まで漏らさない。
- **外部連携（LINE・ペイジェント・giftee・白石CSV）は専用クライアント（Gateway）に隔離**し、シークレットは `.env` → `config/services.php` 経由で読む。
- **業務クエリは Model 層（Eloquentのグローバル／ローカルスコープ）でテナント（保険者ID）に絞る**（テナント越境禁止）。

## 5. データモデル（要件定義書 §6.2・§7.1・§7.2 の個人情報分離方針に基づく設計）

個人情報の分離を前提とする。アプリ（非PII）と個人情報領域（サンプリ）を分ける。
※テーブル設計そのものは要件定義書§7.1により対象外と明記されており、別ファイル「テーブル設計書」の管轄。以下は本リポジトリでの実装向け設計。

| 領域 | テーブル | 主な項目 |
| --- | --- | --- |
| アプリ（非PII） | `app_users` | LINEユーザーID、保険者ID（テナント）、突合キー（ハッシュ）、状態、登録日 |
| アプリ（非PII） | `consents` | ユーザーID、ポリシー版、同意日時 |
| アプリ（非PII） | `survey_responses` | ユーザーID、設問、回答、回答日 |
| アプリ（非PII） | `products` | 商品ID、名称、区分(第2/3類)、価格、対象疾病、供給状況 |
| アプリ（非PII） | `switch_map` | 医療用→OTC、有効成分、監修者・監修日、提示可否 |
| アプリ | `orders` | 注文ID、ユーザーID、明細、金額、利用ポイント、決済トークン(カード番号は非保持)、配送先(PII)、連携状態 |
| アプリ（非PII） | `health_account` | ユーザーID、残高、取引履歴（付与/利用）、**冪等キー** |
| アプリ（非PII） | `exchanges` | 交換ID、ユーザーID、利用ポイント、交換先ギフト、発行コード/URL、状態、**冪等キー** |
| アプリ（非PII） | `contents` / `notifications` / `audit_logs` | コンテンツ・お知らせ・監査ログ |

- 主要テーブルは**保険者ID（テナント）**を持てる設計とする（健保別の可変設定・共同会フェーズに備える）。
- システム名「健康応援口座システム」と、ポイント機能テーブル `health_account` は区別する。

## 6. 横断的な決めごと

### 冪等性

口座残高・ポイント・発注・外部通知を動かす操作は**必ず冪等**にする。
リクエストごとに一意なキー（冪等キー）を持たせ、処理済みキーを記録して二重実行を1回分に抑える。**テストで冪等性を検証すること。**
ポイント値引きは hold（仮押さえ）で確保し、確定なら capture（確定）、取消なら release（解放）に遷移する3状態（hold からの遷移は capture / release の2択）で扱う。

### 整合（決済↔ポイント↔発注）

決済成功 → ポイント減算 → 発注確定を一貫させる。失敗時は返金・ポイント返還（ロールバック）。
外部API呼び出しは失敗・不明を前提に、冪等キー＋ロールバック（または保留→突合で確定）で扱う。

### 個人情報の扱い

- 要配慮個人情報（受診情報等）は**アプリ層に保持しない**。カード番号も保持しない（決済代行でトークン化）。
- 突合キーは**正規化＋ハッシュ**。表示・連絡に要るPIIは可逆暗号化（鍵はアプリ外）。
- 個人を特定できる値をログ・例外・キャッシュ・一時ファイルに残さない。
- 外部サービスへ送信する処理を追加する場合は事前に合意を取る。

### 認証・認可

- **LINE IDトークンは必ずサーバーで検証**（nonce・レート制限・失敗の監査ログ）。
- 会員（LIFF・スマホ限定）と管理画面（別URL・PC・多要素認証・IP制限）は入口・認証・端末ポリシーを分離。
- 端末判定（スマホ限定ガード）はUXであり、セキュリティ境界ではない。

### エラー処理

- 業務エラーは**独自例外**で表現し、`Controller` で対応するHTTPステータスに変換する。
- 例外を握りつぶさない（記録するか再送出）。**例外メッセージにPII・秘密情報を含めない**。
- `Model`・`Gateway` より下の例外（DB・外部API）は `Service` で業務例外に変換して扱う。
