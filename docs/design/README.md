# イベント設計の書き方

画面とバッチのイベント設計を、1画面・1処理ごとに md で置く。
設計する人と Claude Code は、書く前に本書と見本（[`screens/sample.md`](./screens/sample.md)）を読む。

## 1. 設計書との関係

- 全体に共通する規則は、基本設計の参照フォルダ（プロジェクト外。場所は各自の `CLAUDE.local.md` に書く）の設計書（Excel）を正とする。md には写さない。
  - 画面：04 画面設計 4.1〜4.10
  - バッチ：12 バッチ・非同期処理 12.2〜12.4
- API は 06、テーブルは 05、文言は 15 を正とする。md では番号と名称で参照する。
- 画面の配置・寸法・配色・書体は、画面のモックを正とする。md には書かない（04 4.1【役割の分担】）。
- md に定めるのは、画面ごと・処理ごとの項目、イベント、データの読み書き、エラーである。
- 設計書と食い違う事柄や、設計書に足りない事柄を見つけた場合は、md の中で補わず、設計担当が設計書を赤字で修正する。申し送りには書かない。
- Claude Code は設計書を修正しない。食い違う事柄・足りない事柄を見つけた場合は、該当する箇所を `【TBD-番号】` とし、不明点一覧（`<画面ID／バッチID>_unknowns.md`）の「確認したいこと」に、設計書の番号・節・現状・食い違う相手を書く。設計書の赤字の修正は、設計担当（人）が不明点一覧をもとに行う。修正の後、`【TBD-番号】` を実際の値に置き換える。
- md は Claude Code だけが作成・修正する。人は md を直接修正しない。
- 設計書または画面のモックを改訂した場合は、改訂した箇所を変更内容に書き、`screen-design-orchestrator`（バッチの場合は `batch-design-orchestrator`）に変更として依頼する。変更履歴は Claude Code が書く。
- 修正の前に小寺へ相談するかは、次による。

  | 設計書 | 修正の内容 | 相談 |
  |---|---|---|
  | 05 DB設計書 | 誤植の修正・桁数の修正・補足の記入・型の変更 | 不要 |
  | 05 DB設計書 | テーブル・列の追加・削除 | 小寺へ相談する |
  | 05 以外 | すべて | 小寺へ相談する |

- md で新たに用いる文言とエラーは、md とあわせて設計書を赤字で更新する。Claude Code が書く場合は、メッセージID・エラーコードを `【TBD-番号】` とし、不明点一覧に「15 への追加が必要」「06 への追加が必要」と書く。追加と採番は設計担当（人）が行う。
  - 文言：15 メッセージ一覧の別シート「メッセージ」に追加し、メッセージIDを振る（15.2）。
  - エラー：06 の該当する API のエラーに追加する。業務エラーコードは 06 6.1【エラーコード体系】（機能区分＋4桁の連番）により振る。

## 2. 構成

```
docs/design/
├── README.md          … 本書（書き方と雛形）
├── screens/
│   ├── sample.md      … 画面の見本（U-SM-06 注文確認）
│   ├── <画面ID>.md    … 設計書。例 U-LG-01.md
│   └── <画面ID>/      … 設計書以外の成果物。例 U-LG-01/
└── batches/
    ├── <バッチID>.md  … 設計書。例 B-06.md
    └── <バッチID>/    … 設計書以外の成果物。例 B-06/
```

- `screens/`・`batches/` の直下には、設計書（と見本の `sample.md`）だけを置く。不明点一覧（`<画面ID／バッチID>_unknowns.md`）・出典ファイル・レビュー指摘ファイル・変更履歴などの設計書以外の成果物は、ID のフォルダ（例 `screens/U-LG-01/`、`batches/B-06/`）に置く。

- 画面は、1画面を1ファイルとする。ファイル名は画面一覧のID（例 `U-LG-01.md`）とする。
- 空・読込中・失敗・ダイアログなどの状態は、ファイルを分けず、その画面のファイルの中で書き分ける（04 4.3【画面パターン】）。
- 外部の画面（決済 U-SM-08・ポイント交換 U-PT-04・クレジットカード編集 U-PF-03）には、遷移するときに渡す情報と、復帰したときの扱いのみを書く（04 4.3【外部の画面】）。
- `sample.md` のメッセージID（E001 など）は、見本として振ったものであり、15 には登録していない。実際の設計では、15 に文言を追加して ID を振る（1章）。
- バッチは、12.1 の1処理を1ファイルとする。ファイル名は `B-` に 12.1 の No. を2桁で付ける（例 No.6 未完了取引の整理 → `B-06.md`）。

## 3. 書く前に読むもの

Claude Code に書かせる場合も、次を読ませてから書かせる。

| 対象 | 読むもの |
|---|---|
| 共通 | 本書、`screens/sample.md` |
| 画面 | 04 の 4.1〜4.10、画面一覧（要件定義の参照フォルダの `画面一覧.xlsx`）、画面のモック（画面モックの参照先の `screen-mock.html`。必須）、06 の該当する API、05 の該当するテーブル、15 |
| バッチ | 12、11 の別シート「監査ログ対応表」、13 の 13.2・13.6、05 の該当するテーブル |

- 画面の設計には画面のモックを必須とする。モックに枠がない画面は書き始めない。Claude Code に書かせる場合も、対象の画面のモックの枠（状態ごと）を指定する。
- 画面のモックの枠は、枠の表題（`cap` 内の `span.id`）の ID（例：U-LG-01・ERR-01・EMP-01・DLG-01）で区別する。本書ではこれを「枠の ID」と呼ぶ。帯（節）に振られた番号（01〜11）は枠の ID ではない。同じ ID の枠が複数ある場合（例：U-OT-05 の通常と確認ダイアログ）は、ID と表題の名称で特定する（例：U-OT-05「お問い合わせ返信（確認ダイアログ）」）。
- 画面の枠の ID は現行の画面ID（U-LG-01 など）である。エラー・空の状態の枠（ERR-nn・EMP-nn）は、表題の名称の先頭に対象の画面ID を書いている（例：ERR-05「U-SM-06 決済失敗で戻ったとき」）。DLG-nn はダイアログの共通の型の枠である。
- 旧い画面ID（旧U-17 など）は、枠の注記（ID の入れ替え・削除の経緯）にのみ出る。枠の指定・出典には旧い画面ID を用いない。

## 4. 書き方の決まり

### 4.1 文体

- 「である」調で書く。1文には1つの事柄を書き、短く切る。
- 決まっていない事柄は「未定」と書き、推測で埋めない。仮に置いた値は「仮置き」と書き、根拠の箇所を括弧で添える（例 全国一律550円を仮置き。06 グループ3【本グループの前提】）。
- 「未定」は、出典の設計書に未定と書かれている場合に用いる。出典に書かれていない事柄、読み取れない事柄は `【TBD-番号】` とし、不明点一覧（`<画面ID／バッチID>_unknowns.md`）で管理する。不明点一覧は、4.6 の「課題や申し送りの経緯」には当たらない。
- 「仮置き」は、出典の設計書に仮置きと書かれている値に限る。Claude Code は自ら仮置きの値を置かない。

### 4.2 ID と名称

- 画面と API は、先頭の属性（front matter）に ID と名称の対応を書き、本文では名称で示す（例 「注文の確定」。本文に A402 と書かない）。参照の括弧の中では番号を用いてよい（例 （06 A406））。
- テーブルは名称で示す。列は「名称（`物理名`）」と書く（例 注文ID（`order_id`））。
- API の項目は、名称を「」で括り、項目名を添える（例 「決済の結果」（`payment_status`））。
- 値の区分は、表示名と値を併記する（例 完了（`completed`）、決済待ち（1））。

### 4.3 参照

- 設計書は「番号 節【見出し】」の形で参照する（例 04 4.9【復帰後の表示】、06 グループ4【注文ID】、07 7.5【セッションの保持】）。
- 共通の規則は繰り返さない。適用する箇所で参照だけを示す（例 主たるボタンを画面の下端へ固定しない（04 4.2【スクロール】））。
- 全 API に共通するエラー（AUTH-0003・COM-0100・COM-0900）は書かない（04 4.6【共通のエラー】）。

### 4.4 文言

- 画面に表示する文言はメッセージIDで示す（15）。15 にない文言は、15 に追加して振ったIDを書く（1章）。
- 見出し・項目名・ボタン名などの画面の表記は、取得元を「固定」とし、初期値の欄に画面のモックの表記を写す（04 4.4【取得元】）。

### 4.5 表

- 表のセルの中で改行する場合は `<br>` を用いる。
- 同じ扱いの行はまとめてよい（例 No.7〜12）。

### 4.6 書かないもの

- 個人の実データ（氏名・住所・生年月日など）。例示にはダミーの値を用いる。
- 秘密情報（接続情報・鍵・トークン）。
- 実装の方式（コンポーネントの分割、状態の保持の方法など）（04 4.1【対象外】）。ただし、要配慮個人情報などの値を保持する場所は書く（画面の3章）。
- 課題や申し送りの経緯。
- 変更履歴。変更履歴は、Claude Code が参照するファイルとして、設計書とは別のファイルに書く（ファイル名・形式は別途検討）。

## 5. 画面の書き方

見本（`screens/sample.md`）と同じ章立てとする。該当するものがない章も省かず、「なし」「本画面に入力を受ける項目はない」のように書く。

| 章 | 書くこと |
|---|---|
| 先頭の属性 | `id`・`name`・`category`・`authority` は画面一覧に合わせる。`path` は 04 4.3【パス】による（決まっていなければ「未定」）。`mock_id` はモックの枠の ID（3章）。`screens` は遷移元と遷移先の画面、`apis` は呼ぶ API（コメントにメソッドとパス）、`tables` はイベントが呼ぶ API による読み書き（C・R・U・D） |
| 1. 概要 | 画面の目的、法令上の位置づけ、画面に固有の前提、共通の規則のうち特に適用するもの |
| 2. 画面イメージ | モックの枠の ID（状態ごと） |
| 3. 画面の間で引き継ぐ値 | 受け取る元・保持する場所・用いるイベント・破棄する時点。要配慮個人情報と、セッションにかかわる値は、保持する場所を必ず書く |
| 4. 表示項目 | No. は画面イメージの番号と一致させ、上から下・左から右の順に振る。種類は 04 4.4【種類】から選ぶ。取得元は API の名称と項目・固定・メッセージ・画面で計算 のいずれか（04 4.4） |
| 4.1 入力の規則 | 型・桁数・形式・値の範囲・必須。桁数は 05 の定義を超えない（04 4.4【入力の規則】）。入力を受ける項目のみを対象とし、表示のみの項目は対象外とする（型・桁数などを書かず、TBD にもしない） |
| 4.2 表示と活性 | 表示の条件と、非活性とする条件。非活性にするときは、理由をどこで示すかを書く（04 4.4【活性の条件】） |
| 4.3 一覧 | 1件あたりの内容・並び順・件数が多い場合の扱い（04 4.4【一覧】） |
| 4.4 テーブルとの対応 | API の項目ごとに、テーブル・列・変換と算出。対象の行と並び順 |
| 5. イベント | 一覧の表（ID・契機・対象・API・遷移先）と、イベントごとの節。ID は E01 から振り、E01 は初期表示時とする（04 4.5【表示時のイベント】）。契機は 04 4.5【契機】から選ぶ。冪等キーを付ける API は明記する（04 4.9【冪等】） |
| 6. データの読み書き | イベントが呼ぶ API の中で行う読み書きも含めて、イベント・API・テーブル・操作・対象の行・内容を書く。行わない操作（削除など）も明記する |
| 7. エラー時 | 画面に固有のエラー。型は 04 4.6 の①〜⑤から選ぶ |
| 8. 状態 | 通常・読込中・失敗・空（04 4.7）と、画面に固有の状態。設けない場合は理由を書く |
| 9. 権限 | 利用できる者（04 4.10） |
| 10. 参照 | 参照した設計書の番号と節、画面パターン |

イベントごとの節には、次の項目を書く。

- 遷移元（E01 のみ）
- 前提条件（4.2 の活性の条件と対応させる。04 4.5【前提条件】）
- 処理の内容（番号付きの手順で書く）
- 前提条件を満たさない場合
- エラー時（7章を参照する）

## 7. バッチの書き方

12.1 に挙げた処理ごとに、12.1 の「対象・内容および冪等の担保」を詳しくする。12.2〜12.4 の共通の規則（冪等・リトライ・部分的な失敗・実行の場所・テナント・多重起動・記録・監視）は繰り返さず、処理に固有の事柄と例外のみを書く。

| 章 | 書くこと |
|---|---|
| 先頭の属性 | `id`（B-nn）・`name`・`no` は 12.1 に合わせる。`language` は 12.1【実装】による（Laravel／Python）。`trigger`（タイマー／手動）と `schedule` は 12.1 の起動と時期。`tables` は読み書きするテーブル（C・R・U・D）、`externals` は外部の連携先 |
| 1. 概要 | 処理の目的と、前後の処理との関係（例 No.3 の後に実行する） |
| 2. 起動 | 起動の方法・時期・引数（健保コード。12.4【テナント】）・起動の前提となる条件 |
| 3. 対象の抽出 | 抽出の条件（「未処理」の条件。12.2【判定】）・並び順・1回に扱う件数 |
| 4. 処理の内容 | 番号付きの手順。トランザクションの単位。要配慮個人情報を保持する場所（テーブル・ファイルなど）と、破棄する時点（手順の番号）。扱わない場合は「なし」 |
| 5. 冪等と再実行 | 処理済みの記録と、再実行したときの結果（12.2） |
| 6. データの読み書き | 手順・テーブル・操作・対象の行・内容 |
| 7. 外部との連携 | 連携先・送るもの・受け取るもの。再試行は 13.6【リトライ】による。連携しない場合は「なし」 |
| 8. エラー時 | 件ごとに記録して続ける失敗と、全体を中止する失敗の区別。運用への通知（12.2【部分的な失敗】） |
| 9. 記録 | 監査ログのイベントの種別（11 の別シート「監査ログ対応表」）。アプリログは 12.4【記録】の項目に加えて出すものだけを書く |
