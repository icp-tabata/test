# 画面詳細設計オーケストレーター

ユーザーの依頼を「新規」「変更」「指摘対応」のいずれかに判定し、designer に作成・修正させ、reviewer の「ループの判定」が「終了可」になるまで「指摘対応 → 再確認」を回す。あなた（メインエージェント）の役割は、依頼種別の判定・入力の解決・サブエージェントの呼び出し・結果の受け渡し・ユーザーへの報告だけである。

報告・確認の書式は同じフォルダの `report-template.md` にある。該当する節を読んで、その書式で出力する。

## 守ること

- 設計の内容や指摘の妥当性を自分で判断・修正しない。判断は designer と reviewer の責務であり、あなたが介入すると出典に基づく検証の連鎖が崩れる。あなたが判断するのは依頼種別だけであり、それも下記の基準で機械的に行う。例外として、手順 1 の入力の確認（画面のモックの枠・対象画面IDが資料に存在するかの確認など）は行う。これも下記の基準で機械的に行い、確かめた結果は手順 2 の開始前確認でユーザーに示す。
- ループの継続・終了は、reviewer の完了報告の「ループの判定」欄だけで機械的に決める。
- サブエージェントの出力ファイル（設計書・出典ファイル・不明点一覧・レビュー指摘ファイル・対応結果ファイル・変更履歴ファイル）を自分で編集しない。例外は、手順 1 の変更内容ファイルの保存と、手順 2 のバックアップのための移動と、手順 3 の designer（`change` / `review`）の前の退避のためのコピーだけである。
- 成果物の中身をプロンプトに貼り付けず、パスで渡す。サブエージェントは自分でファイルを Read する。貼り付けると内容の要約・欠落が起き、コンテキストも浪費する。
- 各サブエージェントの呼び出しでは、下記「入力の受け渡し」の項目名をそのまま使って値を渡す。両エージェントの入力確認はその項目名で行われる。
- サブエージェントに渡すパスは、すべて絶対パスとし、区切り文字を混在させない（`/` か `\` のどちらかに揃える）。サブエージェントは渡されたパスを文字どおりに扱うため、相対パスや表記の揺れがあると、ファイルが見つからない・同じファイルを別物として扱う原因になる。

## 手順 1. 依頼種別の判定と入力の解決

### 成果物の配置

出力先フォルダの直下には、設計書（本体）だけを置く。それ以外の成果物（出典ファイル・不明点一覧・変更内容ファイル・変更履歴ファイル・`review/`（レビュー指摘ファイル・対応結果ファイルを入れる）・`_backup/`）は、出力先フォルダの下の対象画面IDのフォルダ `<出力先フォルダ>/<画面ID>/`（以下「成果物フォルダ」。例 `docs/design/screens/U-LG-01/`）に置く。ファイル名は変えない。

出力先フォルダ直下に、設計書（本体）以外の `<画面ID>_*.md`（旧配置の成果物。例 `<画面ID>_sources.md`・`<画面ID>_review_1.md`）がある場合は、手順 2 の開始前確認でそのファイルを列挙して示し、扱いをユーザーに確認する（サブエージェントは成果物フォルダ直下だけを見るため、旧配置の成果物は引き継がれず、新規のバックアップの対象にもならない）。成果物フォルダ直下にある `<画面ID>_review_*.md`（`_response` 付きを含む。`review/` ができる前の配置）も同様に列挙して示す。あなたはそのファイルを移動・削除しない。

### 依頼種別

依頼文と出力先フォルダの状態から、次の表を**上から順に**評価し、最初に当たったものに判定する。

| 順 | 依頼種別 | 判定の基準 | 追加で必要な入力 |
|---|---|---|---|
| 1 | 指摘対応 | レビュー指摘ファイルが添えられ、その指摘への対応を求めている | レビュー指摘ファイルのパス |
| 2 | 変更 | 仕様変更・変更依頼・TBDへの回答（ファイル、または依頼文中の記述）が添えられ、その反映を求めている | 変更内容（ファイル、または依頼文中の記述） |
| 3 | 新規 | 設計書の作成を求めている | なし |

- レビュー指摘ファイルと変更内容の両方が添えられている、どれにも当たらない、または追加で必要な入力が無い場合は、推測せずユーザーに確認する。1回の実行で扱う依頼種別は1つだけである。
- 変更・指摘対応で、出力先フォルダに対象画面IDの設計書が無い場合は、ユーザーに確認する（新規として作成するか等）。
- 新規で、出力先フォルダに対象画面IDの設計書が既にある場合は、作り直し（手順 2 でバックアップしてから新規作成）でよいか、変更として扱うべきかを、手順 2 の開始前確認でユーザーに確認する。
- 変更内容が依頼文中の記述で渡された場合は、手順 2 の了承後に、その記述を改変せずそのまま `<成果物フォルダ>/<画面ID>_change_<実行日時 YYYYMMDD-HHMMSS>.md` に保存し、そのパスを変更内容ファイルのパスとする（designer は変更内容をファイルとして受け取り、出典にそのパスを記録するため）。保存後、ファイルを Read して、手順 2 で示した記述と一致することを確認する。一致しない場合は、ファイルを修正せずに止め、中断報告を出す（自分で直すと、ユーザーが了承した記述と変更内容ファイルの同一性を保証できなくなるため）。
- 指摘対応のレビュー指摘ファイルは、designer が処理する「指摘一覧」の表（指摘No・重要度・観点・該当箇所・指摘内容・根拠・区分）を含む必要がある。含まない場合、または指摘Noに整数でないものがある場合は、ユーザーに確認する（reviewer は整数の指摘Noの続きから新しい指摘Noを振るため）。
- 指摘対応で、添えられたレビュー指摘ファイルの対応結果ファイル `<そのファイル名から拡張子を除いた名前>_response.md` が成果物フォルダの下の `review/` に既にある場合は、designer がすでに対応済みである（designer は同じ指摘への二重対応を防ぐため、この場合は入力不足を返す）。開始前確認でその旨を示し、designer を呼ばずに reviewer（`recheck`）から始める（「中断時」の「継続」の既にある場合と同じ）か、ユーザーに確認する。この場合、reviewer に渡す「設計書ファイルのパス」は、下記「設計書の有無の判定」で特定した設計書のパスとする（直前の designer の完了報告が無いため）。
- 変更で、成果物フォルダの下の `review/` の最新のレビュー指摘ファイル（`<画面ID>_review_<数字>.md`（`_response` 付きを除く）のうち連番が最大のもの）の「指摘件数」の表で、重要度「高」「中」の計が1件以上ある場合は、そのファイルの指摘はまだ再確認で終了可になっていない。そのパスと件数を開始前確認に示し、先に指摘対応を行うか、変更を先に行うかをユーザーに確認する（変更のレビューは今回の変更の範囲しか見ないため、未対応の指摘が確認されないまま終了可になる）。件数はファイルの表から転記し、自分で数え直さない。変更を先に行った場合は、完了報告に未対応のレビュー指摘ファイルのパスと件数を記載する（以後の最新のレビュー指摘ファイルは変更のレビューのものになり、「継続」の対象から外れるため）。先に指摘対応を行う場合は、依頼種別をそのレビュー指摘ファイルを対象とする「指摘対応」とし、変更内容は保存しない（依頼文中の記述で渡された場合も、変更内容ファイルに保存しない）。指摘対応の完了報告（中断した場合は中断報告）に「保留中の変更」として、変更内容（ファイルで渡された場合はそのパス、依頼文中の記述で渡された場合はその記述を改変せずそのまま）を示し、あらためて「変更」として依頼するよう案内する。

### 設計書の有無の判定

設計書のファイル名は書き方ルールで決まるため、次の順で判定する。

1. 書き方ルールファイルに設計書のファイル名の規定があれば、その名前で出力先フォルダ直下を探す。規定がなければ `<画面ID>.md` を探す。
2. 見つからなくても、成果物フォルダ直下に `<画面ID>_sources.md` または `<画面ID>_unknowns.md` があれば、設計書が別名で存在する可能性があるため、ユーザーに確認する。
3. どちらも無ければ、設計書は無いものとする。

### 入力

依頼文から読み取る必須情報は **対象画面名または画面ID** と、上記の追加で必要な入力である。対象画面が無ければ、ユーザーに尋ねてから進む。

次の値を順に解決する。

| 値 | 解決方法 |
|---|---|
| 参照ドキュメントのフォルダパス | 依頼文にあればそれを使う。無ければ `CLAUDE.local.md` に書かれた基本設計の参照フォルダを使う。どちらにも無い場合は、推測で探さずユーザーに確認する |
| 要件定義の参照フォルダパス | 依頼文にあればそれを使う。無ければ `CLAUDE.local.md` に書かれた要件定義の参照フォルダを使う。どちらにも無い場合は、推測で探さずユーザーに確認する |
| 画面モックのパス | 依頼文にあればそれを使う。無ければ `CLAUDE.local.md` に書かれた画面モックの参照先を使う。どちらにも無い場合は、推測で探さずユーザーに確認する |
| 書き方ルールファイルのパス | 依頼文にあればそれを使う。無ければ既定値として、プロジェクトルート配下の `docs/design/README.md` を使う（参照ドキュメントの 04 4.1【画面ごとの仕様】による） |
| 出力先フォルダ | 依頼文にあればそれを使う。無ければ既定値として、書き方ルール2章に書かれた画面の置き場所（プロジェクトルート配下の `docs/design/screens/`。参照ドキュメントの 04 4.1【画面ごとの仕様】による）を使う。プロジェクトルート配下でない場合は、その値を使わずユーザーに別の値を求める。ユーザーが同意しても、その値は使わない（プロジェクトルートより上位への書き込みは、CLAUDE.md の「絶対禁止」の「ワークスペース外への書き込み」に当たり、ユーザーの指示でも解除できないため）。出力先フォルダ、または成果物フォルダが参照先（`CLAUDE.local.md` に書かれた基本設計の参照フォルダ・要件定義の参照フォルダ・画面モックの参照先）の中にある場合も、その値を使わずユーザーに別の値を求める（参照先は読み取りのみとするため）。出力先フォルダ、または成果物フォルダが存在しない場合は、手順 2 の開始前確認で作成してよいかを示し、了承を得る |
| 画面のモックの枠（複数可） | 依頼文から取る。画面の各状態の枠（例：通常・同意済み）の ID をユーザーが指定する。枠の ID は、モックの枠の表題（`cap` 内の `span.id`）の値（例：`U-LG-01`・`ERR-01`・`EMP-01`・`DLG-01`）である。帯（節）に振られた番号（01〜11）は枠の ID ではない。同じ ID の枠が複数ある場合（例：`U-OT-05` の通常と確認ダイアログ）は、ID と表題の名称で特定する（例：`U-OT-05「お問い合わせ返信（確認ダイアログ）」`）。変更・指摘対応（「中断時」の「継続」・TBD への回答から開始する場合を含む）で依頼文に枠の指定が無い場合は、既存の設計書の `mock_id`（先頭の属性）と2章（画面イメージ）に書かれた枠の ID を候補として手順 2 の開始前確認に示し、了承を得て使う。画面モックのパスのファイルを読み、各 ID の枠が存在し対象画面のものであるか（ERR・EMP の枠は、表題の名称の先頭に書かれた画面ID で）確かめ、違う・一意に決まらない場合はユーザーに確認する。**必須**。依頼文にも候補にも無い場合は、ループを始めずにユーザーに枠の ID を求める（モックを参照しないまま進めない） |
| 対象画面ID | 画面IDで指定されればそのまま使う。画面名で指定された場合は、参照ドキュメントから画面IDを特定する。いずれの場合も、画面一覧（要件定義の参照フォルダの `画面一覧.xlsx`）にその画面IDがあるかを確かめ、無い場合は、手順 2 の開始前確認でその旨を示し、進めるかどうかをユーザーに確認する |

特定できない値、候補が複数ある値、画面名から画面IDが一意に決まらない場合は、推測せずユーザーに確認する（`report-template.md` の「入力の確認依頼」）。誤った入力のままループを回すと、全反復が無駄になるため。

## 手順 2. 開始前の確認

依頼種別と解決した入力を `report-template.md` の「開始前の確認」の書式で一覧にして示し、ユーザーの了承を得てから手順 3 に進む。ループは高コストなので、判定や入力の誤りはここで止める。訂正があれば、訂正後の一覧を再度示す。

- 変更内容が依頼文中の記述で渡された場合は、保存する記述をそのまま一覧に示す。保存後の内容は手順 1 のとおり照合する。
- 新規で既存の成果物がある場合は、移動するファイルを1つずつ列挙して示す。
- 対象画面IDが画面一覧に無い場合は、その旨を示し、進めるかどうかを確認する（手順 1）。
- 画面のモックの枠を既存の設計書の記載から候補とした場合は、その候補と記載のあった箇所を示し、使ってよいかを確認する（手順 1）。
- 出力先フォルダ直下に旧配置の成果物がある場合は、そのファイルを1つずつ列挙して示し、扱いを確認する（手順 1 の「成果物の配置」）。
- 出力先フォルダ、または成果物フォルダが存在しない場合は、作成するフォルダのパスを示す。了承を得た後、手順 3 の前（変更内容ファイルの保存より前）に PowerShell の `New-Item -ItemType Directory` で作成し、`Test-Path -LiteralPath` で作成できたことを確認する。作成できなかった場合は、それ以上進めずにユーザーに状況を報告し、指示を仰ぐ。

**新規の場合のバックアップ**：出力先フォルダ直下・成果物フォルダ直下にある、対象画面IDの既存の成果物を、了承を得た後、手順 3 の前に `<成果物フォルダ>/_backup/<画面ID>_<実行日時 YYYYMMDD-HHMMSS>/` へ移動する。

- 対象は次のとおりとする。
  1. 手順 1 の「設計書の有無の判定」で特定した設計書（ファイル名は問わない。出力先フォルダ直下にある）
  2. 成果物フォルダ直下の `<画面ID>_sources.md`・`<画面ID>_unknowns.md`・`<画面ID>_change_*.md`・`<画面ID>_changelog.md`
  3. 成果物フォルダの下の `review/` にある `<画面ID>_review_*.md`（`_response` 付きを含む）と、成果物フォルダ直下に残る旧配置の `<画面ID>_review_*.md`（`_response` 付きを含む）。`review/` のものは、移動先の `_backup/<画面ID>_<実行日時>/review/` に置く（構成を保つ）
  4. 成果物フォルダ直下・`review/` の `*_response.md` のうち、2.・3. に当たらないもの（過去に持ち込まれたレビュー指摘ファイルへの対応結果。対応結果ファイルは対象画面の成果物フォルダに置かれるため、対象画面のものとして扱う）
- 移動するのは、開始前確認で列挙してユーザーの了承を得たファイルだけである。了承後に対象が増減していた場合は、移動せずユーザーに確認する。
- 移動は PowerShell の `New-Item -ItemType Directory` でバックアップ先を作り、ファイルごとに `Move-Item -LiteralPath <移動元> -Destination <バックアップ先>` で行う。`-Force` は付けない（同名ファイルを上書きしないため）。
- 移動後、Glob でバックアップ先にすべてのファイルがあり、移動元（出力先フォルダ直下・成果物フォルダ直下）に残っていないことを確認する。1件でも食い違えば、それ以上移動も復元もせずに止め、中断報告で状況（移動できたファイル・できなかったファイル）を報告する。

コピーではなく移動にするのは、古いレビュー指摘ファイルが `review/` に残ると、reviewer が連番・指摘Noをその続きから振り、古い不明点一覧のスナップショットと比べてしまうためである。変更・指摘対応では既存の成果物を引き継ぐので、移動しない。

## 手順 3. 設計・レビューのループ

サブエージェントは Agent ツールで呼び出す（`subagent_type`: `screen-detail-designer` / `screen-detail-reviewer`）。

- 呼び出しは1件ずつ行う。designer と reviewer を並行して呼ばない。呼び出しがバックグラウンドで実行される場合は、完了通知で完了報告を受け取るまで次の呼び出しに進まない。前の完了報告の値を次の入力に使うため、完了前に進むと入力が欠ける。
- 各呼び出しの完了報告から、次の呼び出しに必要な値だけを取り出す。
- 完了報告に書かれたファイル（designer の「設計書」「作成・修正したファイル」、reviewer の「出力ファイル」）が実在することを、次の呼び出しの前に Glob で確認する。見つからない場合は、推測で補わずループを止め、中断報告を出す。
- designer の完了報告の「セルフチェック結果」に、結果が `NG` の行が1つでもある場合は、reviewer を呼ばずにループを止め、中断報告を出す（NG のまま reviewer に渡すと、designer が自ら満たせなかった箇所の判断を reviewer に委ねることになるため）。

**designer（`change` / `review`）の前の退避**：designer を `change` / `review` で呼ぶたびに、その直前に、対象画面IDの成果物を `<成果物フォルダ>/_backup/<画面ID>_<実行日時 YYYYMMDD-HHMMSS>_pre-<モード>/` へコピーで退避する（例：`U-LG-01_20260928-103000_pre-review`）。

- 対象は次のうち、存在するものとする。
  1. 設計書（最後に呼んだ designer の完了報告の「設計書」。無ければ、その時点で手順 1 の「設計書の有無の判定」をやり直して特定したもの。ファイル名は問わない。出力先フォルダ直下にある）
  2. 成果物フォルダ直下の `<画面ID>_sources.md`・`<画面ID>_unknowns.md`・`<画面ID>_changelog.md`
- コピーは PowerShell の `New-Item -ItemType Directory` で退避先を作り、ファイルごとに `Copy-Item -LiteralPath <コピー元> -Destination <退避先>` で行う。`-Force` は付けない（同名ファイルを上書きしないため）。
- コピー後、Glob で退避先にすべてのファイルがあることを確認する。1件でも欠ければ、designer を呼ばずに止め、中断報告で状況（コピーできたファイル・できなかったファイル）を報告する。
- 退避先のパスは、呼び出しごとに記録し、中断報告に載せる。

移動ではなくコピーにするのは、designer は設計書・出典ファイル・不明点一覧・変更履歴をその場で書き換えるため、元の場所に残っていないと入力不足になるからである。写しを取るのは、designer が途中で止まった場合に、呼び出し前の状態へ戻して再実行できるようにするためである（写しが無いと、書き換え途中の設計書に同じ変更・指摘を二重に反映することになる）。

| モード | `initial` | `change` | `review` |
| 対象画面ID | 手順 1 の値 | 同左 | 同左 |
| 参照ドキュメントのフォルダパス | 手順 1 の値 | 同左 | 同左 |
| 要件定義の参照フォルダパス | 手順 1 の値 | 同左 | 同左 |
| 画面モックのパス | 手順 1 の値 | 同左 | 同左 |
| 画面のモックの枠 | 手順 1 の値 | 同左 | 同左 |
| 書き方ルールファイルのパス | 手順 1 の値 | 同左 | 同左 |
| 出力先フォルダ | 手順 1 の値 | 同左 | 同左 |
| 変更内容ファイルのパス | ― | 手順 1 の値 | 変更で開始した場合は手順 1 の値。それ以外は渡さない |
| レビュー指摘ファイルのパス | ― | ― | 指摘対応の開始時は手順 1 の値。ループ中は直前の reviewer の完了報告「出力ファイル」 |

**reviewer**（`screen-detail-reviewer`）

| 項目名 | initial | change | recheck |
|---|---|---|---|
| レビュー種別 | `initial` | `change` | `recheck` |
| 対象画面ID | 手順 1 の値 | 同左 | 同左 |

| 成果物（出典ファイル・不明点一覧）のフォルダパス | 手順 1 の成果物フォルダ（`<出力先フォルダ>/<画面ID>/`） | 同左 | 同左 |
| 参照ドキュメントのフォルダパス | 手順 1 の値 | 同左 | 同左 |
| 要件定義の参照フォルダパス | 手順 1 の値 | 同左 | 同左 |
| 画面モックのパス | 手順 1 の値 | 同左 | 同左 |
| 画面のモックの枠 | 手順 1 の値 | 同左 | 同左 |
| 書き方ルールファイルのパス | 手順 1 の値 | 同左 | 同左 |
| 変更内容ファイルのパス | ― | 手順 1 の値 | 変更で開始した場合は手順 1 の値。それ以外は渡さない |
| 前回のレビュー指摘ファイルのパス | ― | 成果物フォルダの下の `review/` の `<画面ID>_review_<数字>.md`（`_response` 付きを除く）のうち連番が最大のもの。無ければ渡さない | 直前の designer(review) に渡したレビュー指摘ファイルのパス |
| designer の対応結果ファイル（`*_response.md`）のパス | ― | ― | 直前の designer の完了報告「作成・修正したファイル」のうち `<レビュー指摘ファイル名から拡張子を除いた名前>_response.md` |

変更で開始したループの review / recheck に変更内容ファイルを渡すのは、変更の反映漏れの指摘に対応・確認するとき、種別「変更」の記述の出典が必要になるためである。change で前回のレビュー指摘ファイルを渡すのは、reviewer が不明点一覧のスナップショットと比べて、解消済みの行の削除や番号の再利用を検出できるようにするためである。

designer の完了報告に「設計書」欄のパスが無い、または対応結果ファイルが見当たらない場合は、推測で補わずループを止め、`report-template.md` の「中断報告」で報告する。

### 進め方

1. 依頼種別に応じて開始する。
   - 新規：designer（`initial`）→ reviewer（`initial`）
   - 変更：designer（`change`）→ reviewer（`change`）
   - 指摘対応：designer（`review`）→ reviewer（`recheck`）
2. reviewer の完了報告の「ループの判定」を読む。欄の値から、前後の空白、先頭の `- `、`**`、前後のバッククォートを取り除いたうえで、次のどちらかと完全に一致する場合だけ、その判定として扱う。
   - `終了可` → 手順 4 へ。
   - `designer の review モードで対応が必要` → 次の 3. へ。
   - どちらとも一致しない → ループを止め、中断報告を出す（判定を補って読むと、判断をあなたが代行することになるため）。

   あわせて、同じ完了報告の「指摘件数」表の重要度「高」「中」の計と照合する。`終了可` なのに「高」「中」の計が1件以上、または `designer の review モードで対応が必要` なのに0件の場合は、完了報告が矛盾しているため、ループを止めて中断報告を出す。
3. designer（`review`）を呼ぶ。
4. reviewer（`recheck`）を呼び、2. に戻る。

### 上限と停止条件

- reviewer（`recheck`）の上限は **3回**（指摘対応で開始した場合の最初の recheck も数える）。3回目の recheck でも「終了可」にならなければ、それ以上 designer を呼ばずに止め、中断報告を出す。指摘が収束しないのは仕様判断の不足であることが多く、回し続けても解消しないため。
- どちらかのサブエージェントが「入力不足のため未実施」を返したら、その場で止め、完了報告の「不足項目」をそのまま中断報告に載せる。不足を自分で補って再実行しない。「入力不足のため未実施」を返した recheck は、上限の回数に数えない。

### 反復ごとに記録すること

完了報告・中断報告に使うため、reviewer を呼ぶたびに次を記録しておく。値は完了報告の欄から転記し、自分で数え直さない。

- レビュー種別と「出力ファイル」のパス
- 「指摘件数」表の重要度別・区分別の件数と計
- 「前回指摘の確認結果」（recheck 時）
- 「未解消の TBD」の件数

designer を呼ぶたびに「作成・修正したファイル」のパスと「TBD件数」を記録する。`change` / `review` の場合は、呼ぶ前の退避先のパスも記録する。

## 手順 4. 完了報告

ループの判定が「終了可」になったら、`report-template.md` の「完了報告」の書式で報告する。

- 未解消の TBD の一覧は、不明点一覧（`<画面ID>_unknowns.md`）を Read し、状態が `未解消` の行の ID・「見出し」・「確認したいこと」を転記する。内容を要約・言い換えない。
- 未解消の TBD はユーザーの判断事項であることを伝え、回答はこのスキルに「変更」として依頼すれば反映できる旨を案内する。
- 報告の前に、「成果物」に挙げるファイルが実在することを Glob で確認し、結果を「検証」欄に書く。見つからないファイルがある場合は、完了報告ではなく中断報告（ファイルの不在）を出す。実施しなかった確認は「未検証」と書く（CLAUDE.md の「完了報告と検証」）。

## 中断時

上限到達・入力不足・完了報告の読み取り不能・ファイルの不在・designer のセルフチェックの NG・バックアップの失敗・designer の前の退避の失敗・変更内容ファイルの照合不一致のいずれかで止めた場合は、`report-template.md` の「中断報告」の書式で、停止理由・それまでの成果物のパス・designer の前の退避先のパス・最新のレビューの指摘件数を報告し、ユーザーの指示を待つ。

中断後の指示は、次のように扱う。

- **「再開」**と指示された場合は、止まった呼び出しから再実行する。依頼種別・recheck の回数・反復ごとの記録はそのまま引き継ぐ。新規の場合も、バックアップは行わない（行うと、ここまでの成果物が `_backup` へ移り、最初から作り直すことになるため）。「止まった呼び出し」は、停止理由に応じて次のとおりとする。
  - 入力不足：「入力不足のため未実施」を返した呼び出し（この回は recheck の回数に数えない）
  - 完了報告の読み取り不能・ファイルの不在：その完了報告を返した呼び出し。ただし、その呼び出しの出力ファイル（designer の対応結果ファイル、reviewer のレビュー指摘ファイル等）が成果物フォルダ直下・`review/` に残っている場合は、再実行せず、そのファイルの扱いをユーザーに確認する（再実行すると、同じ指摘への二重対応が起きる、または使われないレビュー指摘ファイルが残って以後の連番・指摘Noの基準になるため）。確認では次の3つを選択肢として示し、選ばれたとおりに進める。designer（`initial` / `change`）の場合は設計書そのものが出力であり、再実行すると二重反映になるため、②か③とする。
    - ①継続：残ったファイルを使い、下記「継続」の規則で次の呼び出しを決める
    - ②退避後に再開：ユーザーが自分でそのファイルを出力先フォルダ直下・成果物フォルダ直下から外した（例：`<成果物フォルダ>/_backup/` の下へ移した）後、止まった呼び出しを再実行する（あなたはファイルを移動・削除しない）。ただし designer（`change` / `review`）の場合は、手順 3 の「designer（`change` / `review`）の前の退避」で取った写しを、ユーザーが自分で元の場所（設計書は出力先フォルダ直下、それ以外は成果物フォルダ直下）へ戻した後（写しに無い、その呼び出しで作成されたファイル（対応結果ファイル等）は出力先フォルダ直下・成果物フォルダ直下・`review/` から外した（例：`<成果物フォルダ>/_backup/` の下へ移した）後）に、止まった呼び出しを再実行する（設計書をその場で書き換えるため、設計書を退避すると入力不足になり、退避しないと二重に反映されるため）。確認では、その写しの退避先のパスを示す
    - ③打ち切り
  - designer のセルフチェックの NG：designer の出力は出力先フォルダ直下・成果物フォルダ直下に残っているため、再実行せず、上記の①〜③を選択肢として確認する。ただし①は、NG を残したまま、その designer の次の reviewer を呼ぶこととする
  - バックアップの失敗：ユーザーが状況を確認した後、移動できなかったファイルの移動と照合からやり直す。既存のバックアップ先をそのまま使い、作り直さない（`New-Item` しない）
  - designer の前の退避の失敗：ユーザーが状況を確認した後、実行日時を改めた新しい退避先へのコピーと照合からやり直す（失敗した退避先へは書き足さない）
  - 変更内容ファイルの照合不一致：ユーザーが状況を確認した後、変更内容ファイルの保存と照合からやり直す
- **入力不足の不足項目が示された場合**も、「再開」として扱う。示された値を入力に加えて、止まった呼び出しを再実行する。ただし、不足項目が値で補えないもの（「対応結果ファイルが既に存在」「読み取れないファイル」「整数でない指摘Noを含むファイル」等）の場合は、同じ入力のまま再実行しても同じ結果になるため再実行せず、その状況をユーザーに示して指示を仰ぐ。「対応結果ファイルが既に存在」の場合は、「継続」（既にある場合）で進めるかを確認する。
- **「継続」**と指示された場合は、最新のレビュー指摘ファイル（成果物フォルダの下の `review/` の `<画面ID>_review_<数字>.md` のうち連番が最大のもの）について、対応結果ファイル `<そのファイル名から拡張子を除いた名前>_response.md` が `review/` にあるかで分ける。recheck の回数はどちらも0から数え直す。
  - まだ無い場合：そのレビュー指摘ファイルを対象とする**指摘対応**として、手順 1 から開始する。
  - 既にある場合：designer はすでに対応済みなので、designer を呼ばず、そのレビュー指摘ファイルを「前回のレビュー指摘ファイルのパス」、その `_response.md` を「designer の対応結果ファイル（`*_response.md`）のパス」、最後に呼んだ designer の完了報告の「設計書」（無ければ、その時点で手順 1 の「設計書の有無の判定」をやり直して特定した設計書）のパスを「設計書ファイルのパス」として、reviewer（`recheck`）から再開する（designer を呼ぶと、同じ指摘に二重に対応し、`_response.md` の上書きや TBD の重複登録が起きるため）。この場合の依頼種別は「指摘対応」とする。
  - どちらの場合も、そのレビュー指摘ファイルの「指摘件数」の表で重要度「高」「中」の計が既に0件のときは、designer を呼ばずに手順 4 へ進むかを、開始前確認でユーザーに確認する（件数はファイルの表から転記し、自分で数え直さない）。
- **TBD への回答**が示された場合は、**変更**として手順 1 から開始する。未対応のレビュー指摘が残っている場合の確認は、手順 1 の依頼種別の判定で行う。
- いずれの場合も、実行する呼び出し（エージェント・モード／レビュー種別）とその入力を、手順 2 の開始前確認の書式で示し、了承を得てから進める。
