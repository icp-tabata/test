# 報告書式（screen-design-orchestrator）

SKILL.md の各手順から参照する書式。`<>` は実際の値に置き換える。値はサブエージェントの完了報告・出力ファイルから転記し、自分で解釈・要約しない。

## 入力の確認依頼

手順 1 で値を特定できない、候補が複数ある、画面IDが一意に決まらない場合に使う。

```
## 入力の確認をお願いします

| 項目 | 状況 | 候補・確認した場所 |
|---|---|---|
| <項目名> | <特定できない／候補が複数／画面IDが一意に決まらない> | <候補の一覧、または確認した記載の場所> |

上記の項目について、使用する値をご指示ください。
```

## 開始前の確認

手順 2 で使う。ユーザーの了承を得るまでループを開始しない。

```

次の依頼種別・入力で、レビュー完了まで進めます。

| 項目 | 値 | 根拠 |
|---|---|---|
| 依頼種別 | <新規（designer: initial → reviewer: initial）／変更（designer: change → reviewer: change）／指摘対応（designer: review → reviewer: recheck）> | <依頼文の該当箇所> |
| 対象画面ID | <画面ID>（<画面名>） | <依頼文／参照ドキュメントの該当箇所> |

| レビュー指摘ファイルのパス（指摘対応のみ） | <パス> | <依頼文> |

- 変更内容として保存する記述（変更で、依頼文中の記述で渡された場合のみ）：
  > <依頼文中の変更内容の記述を、改変せずそのまま引用>
- 未対応のレビュー指摘（変更で、最新のレビュー指摘ファイルに重要度「高」「中」が残っている場合のみ）：<最新のレビュー指摘ファイルのパス>（高 <n>件・中 <n>件）。先に指摘対応を行うか、変更を先に行うかをご指示ください。

- 旧配置の成果物（出力先フォルダ直下に、設計書以外の `<画面ID>_*.md` がある場合のみ）：
  - <ファイルの絶対パス>

  - 新規で既存の成果物がある場合、開始前に次のファイルを `<出力先フォルダ>/<画面ID>/_backup/<画面ID>_<実行日時>/` へ移動してバックアップします。
    - <移動するファイルの絶対パス（画面IDで始まらない `*_response.md` を含む）>
  - 新規で既存の設計書がある場合：作り直し（上記のバックアップ後に新規作成）でよいか、変更として扱うべきかをご指示ください。
  - 変更・指摘対応では既存の成果物を引き継ぎ、移動しません。
- 再確認（reviewer: recheck）の上限：3回。重要度「高」「中」の指摘が0件になった時点で終了します。上限に達しても終了可にならない場合は停止して報告します。

この内容で開始してよろしいですか。訂正があればご指示ください。
```

## 完了報告

手順 4 で使う（reviewer の「ループの判定」が「終了可」になったとき）。

```
## 画面詳細設計 完了報告（<画面ID>・<新規／変更／指摘対応>）

reviewer の「ループの判定」が「終了可」（重要度「高」「中」が0件）になったため、ループを終了しました（再確認 <回数>回）。

- 残っている重要度「低」の指摘：<件数>件（<最後のレビュー指摘ファイルのパス>）。実装結果には影響しない指摘のため、対応するかどうかはご判断ください。
- TBD化で対応した指摘：<件数>件（うち重要度「高」<n>件・「中」<n>件）。TBD化は終了の条件上「解消」として扱われるため、内容をご確認ください。
- 保留中の変更（変更の依頼で、先に指摘対応を行った場合のみ）：
  > <依頼文中の変更内容の記述を、改変せずそのまま引用／ファイルで渡された場合はそのパス>

  この変更はまだ反映していません。反映する場合は、あらためて「変更」としてご依頼ください。

### 成果物
- 設計書：<パス>
- 出典ファイル：<パス>
- 不明点一覧：<パス>
- 変更履歴ファイル：<パス／なし>
- 変更内容ファイル：<パス／なし>
- レビュー指摘ファイル：
  - <パス>（<initial／change／指摘対応で渡されたもの>）
  - <パス>（recheck 1回目）
- 対応結果ファイル：
  - <パス>（<対応したレビュー指摘ファイル名>）
- 既存の成果物のバックアップ：<バックアップ先のパス／なし>
- 未対応のレビュー指摘ファイル：<パス>（高 <n>件・中 <n>件。変更を先に行ったため未対応）／なし
  - 対応する場合は、このファイルを添えて「指摘対応」をご依頼ください（最新のレビュー指摘ファイルではなくなったため、「継続」の対象にはなりません）。

### 検証
- reviewer の最終判定：<最後の reviewer の完了報告の「ループの判定」をそのまま転記>（<そのレビュー指摘ファイルのパス>）
- 成果物の実在確認（Glob）：<上記「成果物」のファイルがすべて見つかった>

| 反復 | レビュー種別 | 高（修正要／TBD化） | 中（修正要／TBD化） | 低（修正要／TBD化） | 計 | 前回指摘の確認結果 | 未解消の TBD |
|---|---|---|---|---|---|---|---|
| 1 | <initial／change／recheck> | <n>／<n> | <n>／<n> | <n>／<n> | <n> | <―／OK <n>件／NG <n>件> | <n>件 |
| 2 | recheck | <n>／<n> | <n>／<n> | <n>／<n> | <n> | OK <n>件／NG <n>件 | <n>件 |

### 未解消の TBD（<件数>件）
| ID | 見出し | 確認したいこと |
|---|---|---|
| <ID> | <不明点一覧の「見出し」をそのまま転記> | <不明点一覧の「確認したいこと」をそのまま転記> |

### 次にやること
<該当する項目だけを、番号を振り直して書く>
1. 【あなた】未解消の TBD（上の表）は仕様の判断事項のため、私は決められません。回答は次の一文を、このチャットに送ってください。1件ずつ確認しながら修正を行います。
   > <画面ID> の TBD を解消して
2. 【あなた】残っている重要度「低」の指摘に対応するかを決めてください（残っている場合のみ）。
3. 【あなた】TBD 化で対応した指摘の内容を確認してください（ある場合のみ）。
4. 【あなた】既存の成果物のバックアップ・退避（`_backup/`）を残すか削除するかを決めてください（作られた場合のみ）。
5. 【あなた】成果物のコミットを承認してください（未コミットの場合。コミットは承認を得てから行います）。
```

未解消の TBD が0件の場合は、表の代わりに「なし」と書き、「次にやること」の 1 は省く。

「TBD化で対応した指摘」の件数は designer の対応結果ファイルの「対応結果」列が「TBD化」の行から、重要度別の内訳は同じ行の「重要度」列から転記する（対応結果ファイルが複数ある場合は合算する）。

- レビュー指摘ファイル：<パスの一覧／なし>
