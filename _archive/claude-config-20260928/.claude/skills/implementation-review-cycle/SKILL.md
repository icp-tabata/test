# 製造レビュー サイクル

このスキルが発動したら、3体のレビューサブエージェントを以下の手順・停止条件に従って自分（メインスレッド）が呼び出す。

**このスキル自身がコードをレビュー・修正してはならない。** 役割は次の5つだけである。

1. 3体のレビュアーを、正しい入力で呼び出す
2. 指摘を名寄せし、合否を**機械的に**合成する
3. 停止条件を判定する
4. 各反復の成果物をファイルとして保存する
5. 経過をユーザーに報告する

指摘の妥当性、修正方針の当否、「これは軽微だから通してよいか」の判断は、いずれもあなたの判断事項ではない。**判断したくなったら、それはエスカレーションすべき合図である。**

## サブエージェントとの分担

| 責務 | 担当 |
| --- | --- |
| 仕様適合の検証（テスト実行を含む） | `spec-compliance-reviewer` |
| セキュリティ観点の検証 | `security-reviewer` |
| パフォーマンス観点の検証 | `performance-reviewer` |
| コードの修正 | 実装フェーズ（このスキルの管轄外） |
| 入力の受け渡し、名寄せ、合否合成、停止判定、ファイル保存、報告 | このスキル（メインスレッド） |
| 指摘の妥当性の判断、次工程へ進めるかの判断 | ユーザー |

**サブエージェントはユーザーと直接対話できない。** 入力不足や判断保留は、3体とも「報告に明記して終了する」形で返してくる。**それを受け取ってユーザーに確認するのは、このスキルの責務である。**

## 事前確認

以下を確認する。**この表は3体のレビュアーの必須入力表と一致している。** どちらかを変更した場合、両方を揃えること。

| 確認項目 | 揃っていない場合 |
| --- | --- |
| 3体のレビュアーが利用可能か | **作業を中断してユーザーに報告する。** 代わりに自分でレビューを行わない |
| 対象の画面設計書（実在すること） | **レビューは成立しない。** 受け入れ条件が存在せず、何を基準に合否を決めているのか説明できなくなる。所在を確認する |
| 実装差分の範囲（ブランチ名またはコミット範囲） | 確認する |
| プロジェクトのルール文書（`CLAUDE.md` 等）のパス | 提示を求める。無いと禁止事項の検査基準が無い |
| アーキテクチャ制約・コーディング規約のパス | 提示を求める。無ければその旨をレビュアーに伝える |
| 実装者の完了報告 | 無い場合は「照合対象なし」としてレビュアーに伝える（レビュー自体は実施できる） |
| 成果物の保存先（下記「成果物の保存」） | 既定のパスでよいか確認する |

**この時点でプロジェクトの検査コマンド（lint・型チェック・テスト）が未実行の場合、先にそれらを実行する。** 機械的に検出できる問題をレビュアーに探させるのは、Opusを3体動かす使い方として無駄であり、指摘一覧をノイズで埋めて重大な指摘を埋没させる。**lintエラーが残っている状態でレビューを開始しない。**

## ループ

反復回数の上限は **3回**。1回目は「初回レビュー」を1反復として数える。

```
iteration = 1
history = []

1. 3体のレビュアーを呼び出す。互いに独立しているため、順番に依存関係はなく、
   同時に呼び出してよい。

   iteration == 1（モードA: 初回レビュー）:
     共通の入力: 実装差分の範囲、画面設計書、ルール文書、
                 アーキテクチャ制約・規約のパス
     spec-compliance-reviewer にはこれに加えて、実装者の完了報告

   iteration > 1（モードB: 再レビュー）:
     上記に加えて、各レビュアーに「そのレビュアー自身の前回報告書」と、
     実装側の対応報告（指摘への対応内容）を渡す。
     ※ 他レビュアーの報告書は渡さない。3体の独立性が失われ、
        同じ箇所を同じ見方で見るようになる。

2. 3体の報告を保存する（「成果物の保存」参照）。

3. 指摘を名寄せする（次節「名寄せと合否合成」）。

4. history に {iteration, 各レビュアーの判定, 名寄せ後のCritical/Major/Minor件数,
   再掲件数, 振動の有無, テストファイルの変更有無} を追記する。

5. 停止判定（「停止判定」の表に従って機械的に判定する）。

6. 継続の場合、「戻り対応」を実施し、iteration += 1 として 1. に戻る。
```

---

## 名寄せと合否合成

### 名寄せ

**Critical件数を数える前に、3体の指摘を該当箇所で突き合わせる。** 同一の該当箇所・同一の事象を指す指摘が複数のレビュアーから上がっている場合、**1件として数える**（どのレビュアーが挙げたかは両方記録する）。

3体は観点の境界を守り、管轄外の気づきを「他レビュアー宛の参考情報」欄に回すよう作られているため、重複は多くない。それでも重複は起こる——セキュリティ上の欠陥が同時に仕様違反でもある場合、`security-reviewer` は自分の指摘として出してよいことになっている。名寄せせずに数えると、1つの事象が2件に膨らみ、**反復ごとの件数推移という収束判定の材料そのものが狂う。**

**名寄せは「同じ該当箇所の、同じ事象か」だけで判断する。** 指摘内容を読んで「本質的に同じ問題だろう」と解釈してはならない。それはレビュー内容への判断であり、あなたの役割ではない。判断がつかない場合は名寄せせず、別件として数えた上で、その旨を報告に書く。

### 合否合成

```
critical_total = 名寄せ後のCritical件数

- critical_total == 0 → 合格
- critical_total > 0  → 差し戻し
```

**1体でもCriticalがあれば差し戻し。** 他の2体が合格でも、それによってCriticalが相殺されることはない。

**Major / Minor は合否に影響しない。** 3体のレビュアーも同じ基準で判定するよう作られており、あなたが独自に「Majorが多いから差し戻し」と判断すると、各レビュアーの判定と合成結果が食い違う。Major / Minor は「合格だが残っている問題」として報告に残り、次工程へ進めるかの判断はユーザーが行う。

### 各レビュアーの判定値の扱い

| 判定値 | 合成上の扱い | 報告上の扱い |
| --- | --- | --- |
| `合格` | Critical 0件として合成 | そのまま |
| `差し戻し` | Critical件数を合成 | そのまま |
| `部分レビュー（判定保留）` | **合成しない** | 停止判定の条件1に該当（エスカレーション） |
| `対象外`（`performance-reviewer` のみ） | Critical 0件として合成 | **「対象外」と明記する。合格と混同しない** |

**`対象外` は合格ではなく、「検査していない」という意味である。** 合否合成では合格と同様に扱うが、報告でこの2つを同じ言葉で書いてはならない。合格は「見たが問題がなかった」、対象外は「見る必要がなかったと判断した」であり、後者が誤っていた場合、誰もその領域を見ていないことになる。

## 停止判定

**上から順に評価し、最初に該当したものを採用する。** 判定に迷う余地が生じた場合は、自分で解釈せずエスカレーションする。

| # | 条件 | 判定 |
| --- | --- | --- |
| 1 | いずれかのレビュアーの判定が `部分レビュー（判定保留）` | **エスカレーション**（検査範囲が欠けた状態での合否は意味を持たない） |
| 2 | いずれかの報告の「振動の検知」欄が「なし」以外 | **エスカレーション**（上限回数を待たない） |
| 3 | 前回指摘の解消状況に `不正な解消` / `申告と不一致` / `別経路が残存` / `問題の移動` が1件でもある | **エスカレーション**（上限回数を待たない） |
| 4 | `critical_total` == 0 | **合格**。「終了報告」へ |
| 5 | iteration >= 3 かつ `critical_total` > 0 | **上限到達**。「エスカレーション」へ |
| 6 | 今回のCritical指摘のうち `【前回No.n の再掲】` が付いたものが、前回のCritical件数の半数以上 | **収束していない**。「エスカレーション」へ（上限回数を待たない） |
| 7 | 上記のいずれにも該当しない | 「戻り対応」を実施し、次の反復へ |

**条件3は特に重要である。** `不正な解消` とは、テストの削除・skip化・アサーションの書き換えといった、**指摘を消すための辻褄合わせ**を `spec-compliance-reviewer` が検知した状態を指す。これはプロジェクトのルール文書における絶対禁止事項に直接抵触する。反復を続けて解消する性質のものではなく、**続ければ隠蔽が上手くなるだけである。** 即座に止めてユーザーに上げる。

条件6の「半数以上」は、あなたに判断を求めないための閾値である。各レビュアーが指摘に付す `【前回No.n の再掲】` マークを数えるだけでよい。**指摘内容を読んで「実質的に同じか」を判断してはならない。**

---

## 戻り対応

**3体の指摘を名寄せしてから、1回の修正でまとめて対応する。** 1体ずつ直して都度再レビュー、という進め方をしない。ある観点の修正が別の観点の問題を生むため（認可チェックの追加でループ内クエリが増える、異常系の追加で取得件数の上限が外れる等）、個別に潰すと振動しやすい。

修正は実装フェーズの作業であり、このスキルの管轄外である。**このスキルは修正自体を行わず**、プロジェクトの実装フロー（実装を担当するスキル・サブエージェント、それが無ければユーザー）に、以下を明示して引き渡す。

```
- 対応すべき指摘（3体分を名寄せした一覧。区分・該当箇所・指摘内容・指摘元）
- 指摘されていない箇所は変更しないこと
- テストを通すためにテストの側を変更してはならない。
  既存テストの無効化・skip追加・アサーションの実装出力への追従は、
  プロジェクトのルール文書における絶対禁止事項である。
  テストが通らない場合、通らないまま報告すること。
- 画面設計書の未決事項に該当する箇所は、実装で決め打ちせずエスカレーションすること
- 修正した各箇所に、対応した指摘Noを付記すること
- 対応内容を報告としてまとめること（次回のレビューで照合に使う）
```

**この引き渡し文のうち、テストに関する2項目は省略しない。** レビューを通す圧力の下で最も起きやすい不正が、テスト側の改変によるCritical消しであり、これは絶対禁止事項に直接抵触する。「前回も言ったから分かっているはず」は成り立たない——引き渡しを受ける側は、前回の引き渡しを見ていないことがある。

引き渡し先が特定のスキルである場合、その呼び出しに置き換えてよい。ただし**引き渡す内容（上記5〜6項目）は、呼び出し方が変わっても省略しない。**

## 成果物の保存

**レビュアーは書き込み系のツールを持たない。報告書を保存できるのは、このスキルだけである。** 各反復で以下を保存する。既定のパスは次の通り（**設計書は `hld/` フォルダに置く**のがこのプロジェクトの慣習。事前確認でユーザーに確認する）。

| 成果物 | 保存先 |
| --- | --- |
| 各レビュアーの報告書 | `hld/_screens/_review/<画面ID>_iter<N>_<reviewer名>.md` |
| 名寄せ後の指摘一覧 | `hld/_screens/_review/<画面ID>_iter<N>_merged.md` |
| 実装側の対応報告 | `hld/_screens/_review/<画面ID>_iter<N>_fix.md` |

**上書きしない。** 反復ごとに別ファイルとして残す。

ユーザーが後から「**Criticalがどう解消されたのか、辻褄合わせが紛れていないか**」を確認できるようにするためである。この確認は本サイクル内では行わず、ユーザー自身または別セッションでの監査に委ねる。**このスキルが「不正は無かった」と申告することはできない。** 申告できる立場にいない。

### テストファイルの変更は監査上の重点対象

各反復の引き渡し時にテスト改変を禁じているが、それが守られたかは差分でしか確認できない。`spec-compliance-reviewer` の報告には「テストファイルの変更: あり（内容と妥当性）/ なし」の欄がある。**「あり」だった反復は、報告時にその旨を必ず明示する。** Criticalが0になったことと、テストが変更されていないことは、別々に確認されるべき事実である。

## 終了報告（合格の場合）

以下をユーザーに提示する。省略しない。

- 対象の画面設計書・実装差分の範囲
- 反復回数
- **各反復・各レビュアーの件数推移**（Critical / Major / Minor、うち再掲件数）を表で
- **3体の最終レビュー報告書の全文**
- 過去反復の報告書は、**全文ではなく保存先パスの一覧**を示す（全文は保存済みであり、必要なときにユーザーが開ける）
- **最終反復のテスト実行結果**（`spec-compliance-reviewer` が実行したコマンドと結果）
- **テストファイルの変更があった反復**の一覧（無ければ「なし」）
- **残存するMajor / Minor 指摘の一覧。** Criticalが0でも、これらは消えていない
- 3体の「他レビュアー宛の参考情報」欄の内容（管轄外として指摘一覧に載らなかった事項。埋もれさせない）
- 画面設計書の未決事項のうち、実装フェーズで新たに判明したもの（あれば）
- `performance-reviewer` が `対象外` だった場合はその旨と、対象外と判断した理由

**合格は「Criticalが無い」ことを意味するに過ぎず、「品質が保証された」という意味ではない。** 報告でこの点を曖昧にしない。

PRの作成・マージへ進む場合は、プロジェクトのブランチ運用・承認ルールに従い、ユーザーの承認を得る。

---

## エスカレーション（上限到達・収束せず・部分レビュー・不正な解消）

ループを止め、以下を提示して**ユーザーの判断を仰ぐ**。実装側を勝手にもう一度動かさない。

- **停止理由**（停止判定の表の番号と、その具体的な内容）
- 全反復の成果物の**保存先パス一覧**と、**最新反復の3体の報告書の全文**
- 反復ごとの件数推移（何を直し、その結果どの指摘がどう変化したか）
- 停止理由ごとに、以下を必ず添える。

| 停止理由 | 添えるもの |
| --- | --- |
| 部分レビュー | どの検査が、何が無いために実施できなかったか。**それを揃えれば再開できるのか** |
| 不正な解消 / 申告と不一致 | 該当箇所と、レビュアーが「不正」と判定した根拠、および**該当反復のテストファイルの差分**。これは実装の能力不足ではなく、レビューを通す圧力に対する応答として起きている可能性が高い |
| 別経路が残存 / 問題の移動 | 指摘した箇所は直ったが同じ欠陥が別経路・別箇所に残っている旨と、その箇所 |
| 収束せず / 上限到達 | **繰り返し出ている指摘の該当箇所**。ここは実装の能力不足ではなく、設計書の受け入れ条件が実装困難・矛盾している、あるいはレビュアーとの解釈対立の可能性が高い。**設計書側に戻して見直すべき箇所**として提示する |

いずれの場合も、**人による切り分けが必要な箇所として提示する。** 「もう1回試せば通るかもしれない」という見通しを述べない。それが正しいなら停止条件に該当していない。

## このスキルが発動しない場面

- 対象が画面設計書のレビュー（`screen-design-cycle` の管轄）
- 対応する画面設計書が存在しない変更。受け入れ条件が無いためレビューの基準が成立しない。**この場合はサイクルを回さず、設計書の所在をユーザーに確認する。**
- ユーザーが特定の観点のみのレビューを明示的に求めている場合（例：「セキュリティだけ見て」）。該当するレビュアーのみを単発で呼び出し、サイクルは回さない。**その場合、他の2観点は未検査であることを報告に明記する。**
