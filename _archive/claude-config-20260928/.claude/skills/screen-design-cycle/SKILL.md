# 画面設計 作成〜レビュー サイクル

このスキルが発動したら、`screen-event-designer` と `screen-event-reviewer` の2つのサブエージェントを、以下の手順・停止条件に従って自分（メインスレッド）が呼び出す。

**このスキル自身が設計やレビューの内容を判断・修正してはならない。** 役割は次の4つだけである。

1. 2つのサブエージェントを、正しい順序・正しい入力で呼び出す
2. 停止条件を**機械的に**判定する
3. 各反復の成果物をファイルとして保存する
4. 経過をユーザーに報告する

設計の良し悪し、指摘の妥当性、未決事項の解消可否は、いずれもあなたの判断事項ではない。**判断したくなったら、それはエスカレーションすべき合図である。**

## サブエージェントとの分担

| 責務 | 担当 |
| --- | --- |
| 設計書の作成・修正 | `screen-event-designer` |
| 設計書の検証・指摘 | `screen-event-reviewer` |
| 入力の受け渡し、停止判定、ファイル保存、ユーザーへの報告 | このスキル（メインスレッド） |
| 未決事項の解消、指摘の妥当性の判断 | ユーザー |

**サブエージェントはユーザーと直接対話できない。** 入力不足や判断保留は、両エージェントとも「報告に明記して終了する」形で返してくる。**それを受け取ってユーザーに確認するのは、このスキルの責務である。**

## 事前確認

以下を確認する。**この表は2つのサブエージェントの必須入力表と一致している。** どちらかを変更した場合、両方を揃えること。

| 確認項目 | 揃っていない場合 |
| --- | --- |
| `screen-event-designer` / `screen-event-reviewer` が利用可能か | **作業を中断してユーザーに報告する。** 代わりに自分で設計・レビューを行わない |
| 対象画面の特定 | 推測せず確認する |
| 要件の該当箇所 | 提示を求める（下記参照） |
| UIモックアップのパス（実在すること） | 報告し、代替の入力（画面の説明等）を求める |
| アーキテクチャ制約のパス（実在すること） | 提示を求める。無いまま起動すると designer が即座に終了して返ってくる |
| 設計書の出力先パス | 確認する。既存の設計書があればその配置に合わせる |
| 成果物の保存先（下記「成果物の保存」） | 既定のパスでよいか確認する |
| 今回のトリガー（新規作成／レビュー指摘対応／設計変更） | 推測せず確認する。designer・reviewer に渡すモードを直接左右する |
| （設計変更の場合）変更内容の指示 | 提示を求める |
| （設計変更で未決事項を解消する場合）新しい出典 | 提示を求める。無い場合は該当の未決事項を解消せず維持する旨をdesignerに伝える |
| 共通枠の設計（タブの遷移先・戻るボタンの条件等）の所在 | 現時点では存在しない。存在しないまま進めてよいが、その場合 designer は「共通枠の設計が存在しない」を1件の未決として登録する。画面ごとに同じ未決を繰り返し登録させない |

**要件の該当箇所が提示されていない場合、サブエージェント側で出典検証が省略される。** 着手前にユーザーへ提示を求める。ユーザーが「今は無いので進めて」と明示した場合のみ、**出典検証が省略されること（＝設計書に書かれた要件出典を誰も確認しない状態になること）を承知の上で**進める。この場合、レビュー結果は必ず `部分レビュー（判定保留）` となり、合格は出ない。

## サブエージェントへの入力の渡し方（プロンプトを簡潔に保つ）

サブエージェントは毎回新規に起動され、過去の呼び出しを記憶していない。**したがって必要な情報は毎回渡す必要があるが、渡し方を工夫してプロンプトを短く保つ。**

- **報告書・設計書など、ファイルとして保存済みのものは、内容を貼り付けずパスを渡し、サブエージェント自身に `Read` させる。** サブエージェントはこの目的のために `Read` ツールを持っている。以降のループの疑似コードで「〜のパス」と書かれているものは、すべてこの意味である（内容を貼り付けない）。
- **「要件の該当箇所」「アーキテクチャ制約」は、同一画面の反復中に変わらない限り、初回の呼び出しで提示した内容から変更しない。** 2回目以降の呼び出しでは、内容を再列挙せず「初回提示のとおり（変更なし）」と一言添えるだけでよい。変更がある場合（要件・設計書が更新された等）のみ、変更点を明示する。

## ループ

反復回数の上限は **3回**。**この上限は「セッション」ごとにローカルに数える。** セッションには2種類ある。

- **新規作成セッション**: 1回目は「初回作成→初回レビュー」を1反復として数える。成果物は `<画面ID>_iter<N>.md` として保存する。
- **設計変更セッション**: 合格済み（または進行中）の設計書に対し、レビュー指摘以外の理由（未決事項の解消・要件変更・ユーザーからの変更依頼）で変更を加える場合に開始する、独立したセッション。1回目は「設計変更→設計変更後レビュー」を1反復として数える。成果物は `<画面ID>_change<M>_iter<N>.md`（M＝このセッションの番号。新しい設計変更セッションを開始するたびに M を1つ増やし、N は1から数え直す）として保存する。過去の新規作成セッション・他の設計変更セッションの反復回数とは合算しない。

いずれのセッションも、2反復目以降でレビューにより指摘（Critical）が挙がった場合の修正は、理由によらず常に**モードB（戻り対応）**で行う（「何が理由でこの反復が始まったか」は1反復目だけが持つ性質であり、2反復目以降は「直前のレビュー指摘を直す」という点でセッション種別によらず同じだからである）。

```
iteration = 1
history = []

1. screen-event-designer を呼び出す。

   新規作成セッション・iteration == 1（モードA: 新規作成）:
     入力: 対象画面、要件該当箇所、モックアップのパス、
           アーキテクチャ制約のパス、出力先パス、（あれば）規約・既存設計書

   設計変更セッション・iteration == 1（モードC: 設計変更）:
     入力: 対象画面、要件該当箇所、モックアップのパス、アーキテクチャ制約のパス、
           出力先パス（既存の設計書と同じ）、直前の設計書のパス、
           直前の設計書のスナップショットのパス、変更内容の指示、
           （未決事項を解消する場合）新しい出典のパス、
           `.claude/agents/screen-event-designer-mode-c.md` のパス
           （必ず渡す。渡し忘れるとモードCの規則が一切適用されない）

   いずれかのセッション・iteration > 1（モードB: 戻り対応）:
     入力: 対象画面、要件該当箇所、モックアップのパス、アーキテクチャ制約のパス、出力先パスに加えて、
       - 直前の設計書のパス（designer が直接編集する、生きているファイル。
         通常は初回作成時の出力先パスと同じ）
       - **直前の設計書のスナップショットのパス**（2b で保存した
         このセッションの1つ前の反復のファイル。designer が
         機械的な自己diffに使う「変更前」の基準。生きているファイルと
         同一物を渡さないこと）
       - 直前のレビュー報告書のパス（保存済み。designer が自分で Read する）
     ※ 修正時の禁止事項（指摘外を変更しない、出典をこじつけない、
        未決に回答しない、対応Noを付記する）は designer 側に定義済みである。
        ここで繰り返し指示する必要はない。

2a. designer の報告を保存する（「成果物の保存」参照）。

    報告に「必須入力の欠落により作成できなかった」旨が含まれる場合、
    ループを中断してユーザーに報告する。レビューへ進まない。

2b. **この時点の設計書本体をこのセッションのスナップショットとしてコピー保存する**
    （`cp` 等。新規作成セッションなら `<画面ID>_iter<N>.md`、設計変更セッションなら
    `<画面ID>_change<M>_iter<N>.md`）。設計書は次の反復で designer が
    直接上書きする生きたファイルであり、今コピーしなければこの反復時点の
    内容は二度と再現できない。**コピー後、保存先ファイルが実際に存在する
    ことを確認してから次のステップへ進む。** この確認を省略すると、次回
    レビューの検査I／Jが部分実施にしかならない（「成果物の保存」節を参照）。

3. screen-event-reviewer を呼び出す。

   新規作成セッション・iteration == 1（モードA: 初回レビュー）:
     入力: 設計書のパス、要件該当箇所、モックアップのパス、
           アーキテクチャ制約のパス、（あれば）規約・他画面の設計書

   設計変更セッション・iteration == 1（モードC: 設計変更後レビュー）:
     入力: 設計書のパス、要件該当箇所、モックアップのパス、アーキテクチャ制約のパス、
           直前の設計書のスナップショット、呼び出し元が提示した変更内容の指示、
           designer の報告のパス（変更内容一覧を含む。保存済み。reviewer が自分で Read する）、
           `.claude/agents/screen-event-reviewer-mode-c.md` のパス（必ず渡す）、
           （あれば）規約・他画面の設計書

   いずれかのセッション・iteration > 1（モードB: 再レビュー）:
     入力: 上記に加えて、前回のレビュー報告書のパス、
           designer の報告のパス（「前回指摘への対応表」を含む。いずれも保存済み。reviewer が自分で Read する）
     ※ designer の対応表を渡すのは、reviewer が「申告と実態が食い違っていないか」
        を検査するためである。対応表を渡さないと検査Iが成立しない。

4. reviewer の報告を保存する。

5. history に {iteration, 設計書のパス, レビュー報告書のパス,
   判定, Critical/Major/Minor件数, 再掲件数, 振動の有無} を追記する。

6. 停止判定（次節の基準に従って機械的に判定する）。
```

## 停止判定

**上から順に評価し、最初に該当したものを採用する。** 判定に迷う余地が生じた場合は、自分で解釈せずエスカレーションする。

| # | 条件 | 判定 |
| --- | --- | --- |
| 1 | レビュー判定が `部分レビュー（判定保留）` | **エスカレーション**（検査範囲が欠けた状態での合格・差し戻しは意味を持たない） |
| 2 | レビュー報告の「振動の検知」欄が「なし」以外 | **エスカレーション**（上限回数を待たない） |
| 3 | 検査I／Jに `不正な解消` または `作成者の申告と不一致` が1件でもある | **エスカレーション**（上限回数を待たない） |
| 4 | Critical == 0 | **合格**。「終了報告」へ |
| 5 | iteration >= 3 かつ Critical > 0 | **上限到達**。「エスカレーション」へ |
| 6 | 今回のCritical指摘のうち `【前回No.n の再掲】` が付いたものが、前回のCritical件数の半数以上 | **収束していない**。「エスカレーション」へ（上限回数を待たない） |
| 7 | 上記のいずれにも該当しない | `iteration += 1` として、ループの 1. に戻る |

**条件2・3・6 は、いずれも「反復を続けても解決しない」ことの兆候である。** 上限回数まで回してから報告するのは、ユーザーの待ち時間と計算資源を捨てるだけでなく、3反復ぶんの差分が積み上がって原因の切り分けを難しくする。**早く止めることが目的である。**

条件6の「半数以上」は、あなたに判断を求めないための閾値である。`screen-event-reviewer` が指摘に付す `【前回No.n の再掲】` マークを数えるだけでよい。**指摘内容を読んで「実質的に同じか」を判断してはならない。** それはあなたの役割ではなく、また反復ごとに基準が揺れる。

## 成果物の保存

**サブエージェントは書き込み系のツールを持たない。設計書以外のファイルを保存できるのは、このスキルだけである。** 各反復で以下を保存する。既定のパスは次の通り（**設計書は `hld/` フォルダに置く**のがこのプロジェクトの慣習。事前確認でユーザーに確認する）。

| 成果物 | 保存先（新規作成セッション） | 保存先（設計変更セッション） |
| --- | --- | --- |
| 設計書のスナップショット | `hld/_screens/_history/<画面ID>_iter<N>.md` | `hld/_screens/_history/<画面ID>_change<M>_iter<N>.md` |
| レビュー報告書 | `hld/_screens/_history/<画面ID>_iter<N>_review.md` | `hld/_screens/_history/<画面ID>_change<M>_iter<N>_review.md` |
| designer の報告（対応表・自己点検結果、または変更内容一覧を含む） | `hld/_screens/_history/<画面ID>_iter<N>_designer.md` | `hld/_screens/_history/<画面ID>_change<M>_iter<N>_designer.md` |

**上書きしない。** 反復ごとに別ファイルとして残す。設計変更セッションの命名は既存の新規作成セッションのファイル（`_iter<N>.md` 等）と衝突しないよう、必ず `_change<M>_` を挟む。

**「設計書のスナップショット」は、次回レビューの検査I／J（変更の混入）と designer の自己点検が機械diffで機能するための前提であり、かつユーザーが後から「本当に指摘を直しただけか、辻褄合わせの捏造が紛れていないか」を確認するための唯一の手段でもある。** これが欠けると、指摘対象以外に何が変わったかを確認する手段が失われる。設計書だけが残っていても、どの指摘に対して何を変えたのかは追えない。3点セットで初めて追跡できる。

この確認自体は本サイクルの中では行わない。必要であればユーザー自身、または別セッションでの監査に委ねる。**このスキルが「捏造は無かった」と申告することはできない。** 申告できる立場にいない。

## 終了報告（合格の場合）

以下をユーザーに提示する。省略しない。

- 最終版の設計書のパス
- 反復回数
- **各反復の件数推移**（Critical / Major / Minor、うち再掲件数）を表で
- **最終レビュー報告書の全文**
- 過去反復のレビュー報告書は、**全文ではなく保存先パスの一覧**を示す（全文は保存済みであり、必要なときにユーザーが開ける）
- **未決事項一覧の全件**（0件の場合はその旨。0件は疑わしいので、`screen-event-designer` の報告に含まれる「なぜ0件なのか」の説明をそのまま添える）
- 最終レビューの検査範囲（未実施の検査があれば、その内容と理由）

**合格は「Criticalが無い」ことを意味するに過ぎず、「設計が正しい」という意味ではない。** 残存するMajor / Minor は消えていない。報告でこの点を曖昧にしない。

未決事項が1件でもある場合、その解消（人による判断）を待たずにこのサイクルを完了として扱ってよいが、**後続の製造工程には未決事項一覧を必ず引き渡す**旨を明記する。

**合格した設計書（`hld/_screens/<画面ID>_<画面名>.md`）が、製造工程へ渡す正の成果物である。** Excelへの転記は行わない。設計書の本文にレビュー対応の痕跡（`<!--` で始まるコメント）が残っていないことを確認してから提示する。新規作成または設計変更の確定物として次工程に渡す前に、ユーザーの承認を得る。

---

## エスカレーション（上限到達・収束せず・部分レビュー・不正な解消）

ループを止め、以下を提示して**ユーザーの判断を仰ぐ**。設計サブエージェントを勝手にもう一度呼び出さない。

- **停止理由**（停止判定の表の番号と、その具体的な内容）
- 全反復の成果物の**保存先パス一覧**と、**最新反復のレビュー報告書の全文**
- 反復ごとの件数推移（何を直し、その結果どの指摘がどう変化したか）
- 停止理由ごとに、以下を必ず添える。

| 停止理由 | 添えるもの |
| --- | --- |
| 部分レビュー | どの検査が、何が無いために実施できなかったか。**それを揃えれば再開できるのか** |
| 振動 / 不正な解消 | 該当箇所と、reviewer が「不正」と判定した根拠。**これは設計側の能力不足ではなく、指摘の趣旨が伝わっていないか、指摘自体が実行不能である可能性が高い** |
| 収束せず / 上限到達 | **繰り返し出ている指摘の該当箇所**。ここは設計側の能力不足ではなく、要件そのものが確定していない、あるいは reviewer との間で解釈の対立がある可能性が高い |

いずれの場合も、**人による切り分けが必要な箇所として提示する。** 「もう1回試せば通るかもしれない」という見通しを述べない。それが正しいなら停止条件に該当していない。

## このスキルが発動しない場面

- 対象が画面詳細設計以外（バックエンド設計、アーキテクチャ決定、API仕様等）
- ユーザーが明示的に「レビューは後でいい、まず素案だけ」等、サイクルを回さず単発の作成を求めている場合。この場合は `screen-event-designer` のみを呼び出し、**レビューを行っていない旨を報告する**。レビュー未実施の設計書を、合格した設計書と同じ顔で次工程に渡さない。
- ユーザーが既存の設計書のレビューのみを求めている場合。この場合は `screen-event-reviewer` のみを単発で呼び出し、サイクルは回さない。
- 実装済みコードのレビュー（`implementation-review-cycle` の管轄）
